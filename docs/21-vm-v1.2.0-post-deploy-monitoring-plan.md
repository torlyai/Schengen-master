## 1. Purpose & scope

v1.2.0 ships **4 features** to the Chrome Web Store without:
- Automated detection.spec.ts coverage of the core slot detector.
- Real TLS DOM fixtures (placeholder `.keep` files only).
- Live integration tests against Stripe + Supabase in CI.

These gaps existed in v1.1.0 too — v1.2.0 doesn't introduce them, but doesn't close them either. **This plan documents how we'll monitor in production to compensate.**

The window covered: from CWS submission through ~30 days post-launch.

## 4. Phase 1 — CWS review window (T-0 to ~T+3d) — ✅ COMPLETED 2026-05-22

**Goal:** v1.2.0 passes review without rejection.

**Outcome:** v1.2.0 submitted 2026-05-18, approved 2026-05-22 (~4-day review window). No rejection or rework needed. Now live at https://chromewebstore.google.com/detail/cpogdllkcpenafboclnidfmmlcnjpbfm.

The §4.1 daily checks and §4.2 pre-approval probes below are retained for reference if a future release ends up in the same window.

### 4.1 Daily checks (5 min/day)

- Open https://chrome.google.com/webstore/devconsole/
- Check status of v1.2.0 submission. States to watch for:
  - **Pending review** → keep waiting
  - **In review** → keep waiting
  - **Published** → move to Phase 2
  - **Rejected** → diagnose: read rejection reason, prepare fix, resubmit. v1.1.0 stays live throughout.

### 4.2 Pre-approval cross-checks

While awaiting review, sanity-check the production backend (deployed earlier today) is responding correctly:

```bash
# Probe 1: /license/activate rejects missing IDs (proves new code is live)
curl -X POST https://torly.ai/api/visa-master/license/activate \
  -H 'Content-Type: application/json' \
  -d '{"installId":"00000000-0000-0000-0000-000000000000"}'
# Expected: 400 "Provide sessionId or setupIntentId"

# Probe 2: /booking/refund rejects short evidence (proves PRD 20 Zod schema is live)
curl -X POST https://torly.ai/api/visa-master/booking/refund \
  -H 'Content-Type: application/json' \
  -d '{
    "installId":"00000000-0000-0000-0000-000000000000",
    "licenseToken":"any-string-twenty-chars-long",
    "stripePaymentIntentId":"pi_test",
    "evidenceText":"short"
  }'
# Expected: 400 "Invalid body" — Zod rejects evidenceText <20 chars

# Probe 3: /notify/email responds (proves N-3b backend is in place)
# (Will reject without licence, but should not 404 — confirms route exists)
curl -X POST https://torly.ai/api/visa-master/notify/email \
  -H 'Content-Type: application/json' \
  -d '{"installId":"00000000-0000-0000-0000-000000000000"}'
# Expected: 4xx with a meaningful error, NOT a 404 page
```

### 4.3 What to do if rejection happens

1. Read the CWS rejection email. Common categories:
   - **Permissions**: usually a new permission auto-detected. We didn't add any — flag this as an audit error and respond.
   - **Single-purpose policy violation**: shouldn't apply; the extension's purpose is monitoring TLScontact for a specific user.
   - **Privacy / data handling**: unlikely given the architecture. Worst-case prepare disclosure update.
   - **Manifest issue**: rebuild + resubmit.
2. Fix the cited issue.
3. Bump to v1.2.1 if a code change is required (NOT v1.2.0-resubmit — CWS treats it as a new package version).
4. Update `extension/manifest.json` + commit + push + tag + zip + resubmit.
5. v1.1.0 stays live throughout.

## 5. Phase 2 — Post-approval rollout (T+approval to T+24h)

**Goal:** users auto-update from v1.1.0 to v1.2.0 without issues.

### 5.1 First-hour checks (within 1h of approval)

1. **Confirm Web Store listing shows v1.2.0** — visit listing as anonymous, verify version string.
2. **Test installing fresh** — install in a new Chrome profile, verify welcome page renders, premium intro opens, manifest shows 1.2.0.
3. **Test upgrade path** — in a profile with v1.1.0, force an update check (`chrome://extensions` → click ↻ on the card → "Update"). Verify v1.2.0 lands; check `chrome.storage.local` to confirm settings, target, license all preserved.

### 5.2 Auto-update rollout (first 24h)

Chrome's default extension update interval is ~5 hours. Within 24h, the vast majority of v1.1.0 users will be on v1.2.0.

- **Watch for**: support tickets mentioning "extension stopped working", "lost my settings", "in-progress booking disappeared".
- **Channel**: support@torly.ai — already wired in Settings page.
- **Response time goal**: <4 hours during business hours for the first 7 days.

### 5.3 First-Premium-activation smoke test

If a real Premium activation happens within the first 24h post-rollout:
- Watch `vm_installs` for the new install row.
- Verify the new metadata columns are populated:
  ```sql
  SELECT install_id, extension_version, browser_name, os,
         attribution_source, preferred_email_locale, created_at
  FROM visa_master_installs
  ORDER BY created_at DESC LIMIT 5;
  ```
- Verify the welcome email was sent (Resend dashboard or `vm_notifications_sent` table).

## 7. Phase 4 — Quality investments for v1.3 (T+7d to T+30d)

These are pre-existing test-coverage gaps that v1.2.0 didn't fix but that should be addressed before v1.3 ships. Order by ROI:

### 7.1 Capture TLS DOM fixtures (HIGH ROI, ~30 min)

Per `extension/test-fixtures/tls-dom/README.md`, capture real TLS HTML for at least:

- `uk-manchester/login.html` — to validate auto-login selectors
- `uk-manchester/booking-no-slots.html` — to validate NO_SLOTS detection
- `uk-manchester/booking-slot-available.html` — to validate SLOT_AVAILABLE detection
- `uk-manchester/logged-out.html` — to validate LOGGED_OUT detection

Use Chrome DevTools Local Overrides (Sources → Overrides → Save for overrides) on the real TLS page, redact PII, commit.

### 7.2 Write `detection.spec.ts` (HIGH ROI, ~1 hour)

Once fixtures exist, add a Playwright spec that:
1. Loads each fixture into a test page.
2. Injects the content script.
3. Asserts the resulting `ExtState` matches expectation.

This becomes a CI gate: any future change to `detector.ts` that breaks a real-DOM case fails the build.

### 7.3 Write `booking-fsm.spec.ts` (MEDIUM ROI, ~2 hours)

Mock `chrome.alarms` time + `chrome.storage`. Assert:
- Capture → schedule alarm at +24h
- Alarm fires → activeBooking → previousBooking + state → PREMIUM_ACTIVE
- Refund within 24h → activeBooking cleared, alarm cleared
- Stop watching → state → PAUSED
- Migration: stranded activeBooking → handled on SW startup

This is currently untested logic, all introduced in v1.2.0.

### 7.4 Wire popup "Send test email" button (LOW-MEDIUM ROI, ~30 min)

`testEmailConnection()` exists; popup UI button in P-12 Options doesn't call it. Add a button + label + result toast.

### 7.5 Build `license-watch.ts` (LOW ROI for now, ~3 hours)

To complete N-3b's deferred events. Polls `/license/status` daily; fires `vm_license_expiring` (≤30 days) and `vm_license_deactivated` (when status flips). Currently licences last 18 months so urgency is low — defer to v1.4+ unless a user complaint surfaces.

### 7.6 Backend smoke-test of N-8 evidence in CI (LOW ROI, ~30 min)

Add a torlyAI Playwright e2e: simulate a Stripe webhook → real DB write → curl `/booking/refund` with evidenceText → assert column populated. Catches schema drift.

## 8. Detection-specific monitoring

**The single biggest "we hope this still works" path in the codebase.**

### 8.1 Background

`detector.ts` and `content-script.ts` are byte-identical between v1.1.0 (live) and v1.2.0 (shipping). The risk surface is therefore unchanged — but it's also untested in CI.

### 8.2 Production signals to watch for

| Signal | Where | What it means |
|---|---|---|
| Spike in `UNKNOWN` state classifications | (would need analytics — not yet wired) | TLS DOM has changed; detector's selectors are missing |
| Users emailing support "no slots detected" | support@torly.ai | Same as above — manual aggregation |
| Users emailing support "extension says wrong page" | support@torly.ai | WRONG_PAGE state firing incorrectly; URL pattern may have changed |
| Spike in `CLOUDFLARE` state | (n/a — no analytics) | TLS rolled out new Cloudflare config; not necessarily a bug |
| Sudden drop in slot-found events for active users | (Telegram/email analytics on our side) | Detector silently broken; people not getting notifications they should |

### 8.3 What to do if R-2 (TLS DOM change) is suspected

1. Reproduce: open real TLS page, watch extension behaviour.
2. Capture: inspect the new DOM (Chrome DevTools) — what selector is missing?
3. Add fallback selector: edit `detector.ts` selector arrays to include the new pattern, keeping the old one as fallback.
4. Ship a hotfix v1.2.1.

Because the architecture has redundant selector chains, **a single TLS DOM change rarely breaks detection entirely** — usually 2-3 selectors still match.

### 8.4 Manual quarterly check (you, no code)

Once a quarter, dogfood the extension against the real TLS page on the centres you care about (e.g. UK→France). Confirm:
- Slot-available state renders correctly
- No-slots state renders correctly
- Logged-out state renders correctly
- Cloudflare state renders correctly (if you trigger one)

If anything is wrong → file an internal bug → see §8.3.

## 9. Rollback playbook

### 9.1 Soft rollback — emergency hotfix

If v1.2.0 has a critical bug discovered post-rollout:

1. **DON'T** try to downgrade users from v1.2.0 → v1.1.0. Chrome doesn't support that.
2. **DO** ship v1.2.1 with the fix immediately. Same workflow:
   - Bump manifest to 1.2.1
   - Fix the bug on `feat/vm-v1.2.1-hotfix-*` branch
   - PR + merge to main
   - Tag v1.2.1, push tag
   - Build + zip
   - Upload to CWS
   - Mark as urgent in submission notes

### 9.2 CWS publish-then-pull

If you need v1.2.0 OFF the Web Store immediately:
1. CWS Developer Dashboard → Visa Master listing → **Unpublish item**.
2. Users who already auto-updated stay on v1.2.0 (you can't pull back from their browsers).
3. New installs get nothing until you republish.
4. Use only for serious-incident cases.

### 9.3 Republish previous version

CWS has a "Republish a previous version" option in the dashboard. This re-pushes v1.1.0 as the published version:
1. New installers get v1.1.0 again.
2. v1.2.0 users who already auto-updated **stay on v1.2.0** — they don't auto-downgrade.
3. Useful for stopping the v1.2.0 spread while you ship v1.2.1.

### 9.4 Backend-side mitigations

If a v1.2.0 bug requires backend help:
- The backend can refuse to issue refunds with bad evidenceText (already does — Zod 400).
- The backend can flag installs with anomalous metadata (e.g. extensionVersion='1.2.0' AND a known-bad pattern).
- The backend can stop sending email events for affected installs (Resend pause).

Stripe / Supabase / Resend dashboards are the operational tools here.

## 10. Operational dashboard queries

Until PRD 17's ops dashboard is fully built, these SQL queries against Supabase give visibility.

### 10.1 Active installs over time

```sql
SELECT DATE_TRUNC('day', activated_at) AS day,
       count(*) AS new_premium_installs
FROM visa_master_installs
WHERE status = 'active' AND activated_at IS NOT NULL
GROUP BY 1
ORDER BY 1 DESC LIMIT 30;
```

### 10.2 Extension version distribution (post-v1.2.0)

```sql
SELECT extension_version, count(*) AS installs
FROM visa_master_installs
WHERE status = 'active'
GROUP BY extension_version
ORDER BY installs DESC;
```

A healthy rollout shows v1.1.0 shrinking and v1.2.0 growing over the first 48h post-approval.

### 10.3 Booking funnel

```sql
SELECT
  count(*) FILTER (WHERE status = 'captured') AS bookings_captured,
  count(*) FILTER (WHERE status = 'refunded') AS bookings_refunded,
  count(*) FILTER (WHERE status = 'disputed') AS bookings_disputed,
  count(*) FILTER (WHERE status = 'captured' AND captured_at > NOW() - INTERVAL '7 days') AS captured_last_7d
FROM visa_master_bookings;
```

### 10.4 Refund evidence audit (N-8)

```sql
-- Refunds with suspiciously short evidence
SELECT install_id,
       length(refund_evidence_text) AS len,
       refund_evidence_text
FROM visa_master_bookings
WHERE status = 'refunded' AND refund_evidence_text IS NOT NULL
ORDER BY len ASC LIMIT 20;

-- Identical evidence across installs (potential paste copy)
SELECT refund_evidence_text, count(DISTINCT install_id) AS installs
FROM visa_master_bookings
WHERE status = 'refunded' AND refund_evidence_text IS NOT NULL
GROUP BY refund_evidence_text
HAVING count(DISTINCT install_id) > 1;
```

### 10.5 Attribution mix (PRD 17)

```sql
SELECT attribution_source,
       count(*) AS installs,
       round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS pct
FROM visa_master_installs
WHERE status = 'active' AND attribution_source IS NOT NULL
GROUP BY attribution_source
ORDER BY installs DESC;
```

### 10.6 Email delivery health (N-3b)

```sql
SELECT email_event_type,
       count(*) AS attempted,
       count(*) FILTER (WHERE resend_email_id IS NOT NULL) AS delivered,
       count(*) FILTER (WHERE resend_email_id IS NULL) AS missing_resend_id
FROM vm_notifications_sent
WHERE sent_at > NOW() - INTERVAL '7 days'
GROUP BY email_event_type;
```

If `missing_resend_id` is non-zero for any event type, that's a Resend / backend dispatcher issue worth investigating.
